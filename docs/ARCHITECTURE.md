# Architecture and boundaries

## Independent services and resume adaptation (2026-11-17)

The Worker executable supports separate `--ServiceRole search` (default) and `--ServiceRole monitor` hosts. Search claims non-integration tasks; Monitor claims only Integration tasks. Each role has an exclusive process file lock, an independent cancellation scope and a persisted heartbeat. `AddWindowsService` supports JobFlow.Search and JobFlow.Monitor in SCM; the API can start/pause/stop either role through fixed service names or a trusted configured Worker executable for local development. Windows registration requires an administrator and the same user identity that owns Codex authentication and DPAPI keys.

Search owns persistent Chromium. API forwards manual browser operations to the loopback search host (5272). Scheduled search executes locally in the Search process and does not depend on API availability. Monitor (5273) reads Gmail/status sources independently, optionally invokes its assigned CLI agent and emits notifications. Production search never polls mail; the old combined path remains only for compatibility fixtures. Search completes a platform before visiting the next, rotates the first platform between runs and processes newest publications first within the configured total budget.

TaskSchedule computes intervals anchored to the previous cadence, daily local times or selected weekdays. Missed intervals are skipped. Invalid local times move to the first valid minute; ambiguous fall-back times use the earlier occurrence once. TimeZone is used in calendar calculations. Task results, approval requests and employer feedback produce durable Notification records.

ResumeAgentService extracts text with PdfPig. CLI selection returns an owned uploaded version ID. CLI adaptation returns text sections and exact evidence quotes; a separate CLI task verifies factual support. Playwright renders encoded plain text into a simple PDF with no external resources. Generated files live under resumes/generated and ResumeVersion records include Origin, SourceResumeVersionId, VacancyId, AgentExecutionId, AdaptationJson and DossierHash. Application.ResumeVersionId identifies the actual uploaded bytes. A changed dossier blocks submission of a previously generated PDF. This is model-assisted factual checking, not a formal guarantee; initial human review remains appropriate.

Dossier extraction produces a DossierProposal. Exact source quotes are validated, and only explicit confirmation replaces the profile fields. Scanned PDFs without readable text require external OCR. Browser freshness checks require a resolvable publication date, exact observed evidence and open status; they run during evaluation and again before form filling. Unknown dates and closed/stale vacancies stop automatic submission.

Domain holds entities, ownership IDs and states. Application holds contracts, rules, templates and transition policy. Infrastructure implements EF SQLite, durable workflow, CLI/browser/MCP, imports and task processing. API serves localhost/private-LAN operations and Angular. Worker runs separately against the same JOBFLOW_DATA_DIR.

## Browser workflow

The browser snapshot scopes controls/text to the active dialog before applying the 250-control limit and excludes on-screen controls covered at their hit point. Each agent invocation explicitly explains activeDialog and lastActionError, including for existing stored agent profiles. Safe action timeouts/stale controls are fed back with a refreshed snapshot, with a bounded per-stage recovery budget. Uploads and final submission are never replayed by this recovery loop. Navigation uses configurable timeouts and bounded GET retries; task cancellation still ends the stage. Defaults: 60s navigation, one navigation retry, 8s action, three action recoveries (Browser configuration in both API and Worker).

Every browser CLI call receives bounded stage memory: the last twelve actions, target labels, outcomes, errors and whether the next observation changed. Raw input values and obsolete target IDs are not included in this history. Collected vacancy links remain in the search task context. A repeated page state produces a warning on its third visit and stops the stage on its eighth visit within sixteen observations; new collected vacancies count as progress. Memory is scoped to one search/application stage, not shared between profiles or retained as a cross-run conversation. Durable application records still prevent repeat applications across runs.

Search snapshots also expose the last twenty observed same-platform GET pages, with exact URLs and bounded titles. Search may return to these pages or follow current observed links; application navigation still requires current links. Returns use GET navigation, never browser POST history. Trace and action outcome events distinguish requested and actual URLs, including rejection reasons. Search instructions include the remaining step budget and require finishing before opening another vacancy at the end of the budget.

Snapshots include semantic/focusable custom dropdowns, visible labels for hidden filter radios, and short clickable custom options. Expanded state participates in target revalidation. Before observation, the driver waits for same-platform document/fetch/XHR requests and stable visible text/URL, with a four-second bound; this accommodates asynchronous filter updates without waiting indefinitely for background activity. Native select actions remain restricted to SELECT elements.

Validated discoveries are checkpointed to SQLite at every collect/finish, deduplicated by platform and external vacancy ID. The configurable Browser.DiscoveryLimit defaults to fifty (allowed range 1–50). A later discovery failure preserves these vacancies but skips evaluation and submission for that platform in the failing run; other selected platforms continue. A subsequent run can rediscover the same vacancy without creating another row. Failure diagnostics include bounded control metadata without field values.

Before a control action, the driver observes the page again and prefers the original DOM node with matching semantics. After SPA replacement it accepts only a single matching labelled/named/link target; disappearance or ambiguity is returned for replanning without clicking. A changed URL requires a new decision. Final submission keeps its separate durable attempt and is never automatically repeated.

Terminal browser failures retain a bounded error, visible page text, URL and password-masked viewport JPEG in browser-diagnostics under Storage.Root before the automation tab closes. An audit event, WorkflowRun.Error and task history identify the failure and diagnostic UUID. API read endpoints expose its metadata and image to local/LAN clients; the UI links them from history rows. Captures remain local until explicitly removed and can contain visible personal data. Diagnostic capture failures do not replace the browser error. Submission timeouts still become SubmissionUnknown with no automatic second click.

WorkflowDefinition.ExecutionMode selects `prepare` (existing API/import preparation) or `browser`. Browser mode has one saved BrowserProfileId and a BrowserAutomation agent. The agent receives readable DOM text and observed control IDs, returns a schema-validated action, and BrowserWorkflowDriver executes it in the persistent Playwright context. Password/hidden fields are omitted; arbitrary selectors, JavaScript and filesystem paths are not accepted from the model. The selected resume is the only upload source. Pages from the same site, including accessible frames, are supported; unsupported navigation or fields stop the affected application.

Search owns BrowserSessions, so manual login, the LAN browser view and automated work share actual cookies. API proxies browser controls to the loopback Search host. Search executes its workflow locally; the old API browser-run endpoint remains for compatibility tests. Profile gates prevent two automation runs from controlling one profile at once; manual input is unavailable while the agent holds its lease. The web UI can display JPEG screenshots and relay explicit user clicks, text and keys for manual login from another LAN computer.

BrowserSubmissionService stores a unique candidate/canonical-URL attempt and Submitting state transactionally before the final click. It performs no second submission after an unknown outcome. Visible confirmation is required for Confirmed/Submitted; missing receipts, timeouts and interrupted attempts become SubmissionUnknown. Existing submitted/imported applications and duplicate platform configurations block repeat applications. Automatic submission requires browser mode, AutoSubmit and an AI evaluation of Proceed. NeedsReview remains ReadyForReview. Gmail runs in the independent Monitor role according to its integration task schedule.

## Workflow and consistency

EvaluationEvidence normalizes only controlled equivalent skill names (for example SQL Server / MS SQL Server), Unicode whitespace and equivalent .NET major-version spelling. Versions, related technologies, proficiency and experience duration are never inferred. Structured rules and AI validation use the same skill keys. Every evaluation invocation receives candidateSkills and runtime instructions to return those names in matches; stored agents need no manual template update. Other dossier facts remain available for rationale, but a mention outside the confirmed Skills field is recorded only as an unverified mention, including negative mentions.

Validated AI evaluations retain a bounded validation object inside the existing ResultJson: execution ID, original decision/rationale/matches, per-claim status, matched candidate skill and source, unsupported mentions and warnings. An EvaluationValidated audit links it to the application. The evaluation is committed before an unsupported match blocks preparation/submission, so the UI's existing rationale/clarifications show the specific issue and a corrected retry creates another historical evaluation. Truncated claim diagnostics (over 100 claims or 200 characters per claim) never permit automatic acceptance. Proceed combined with missing skills or unverified requirements becomes NeedsReview and cannot trigger automatic submission. No database migration is required; older evaluation JSON remains readable.

WorkflowDefinition binds a profile, a selection of platforms, a resume version, rules and optional evaluator/writer. A conditional lease prevents overlapping runs. Discovery uses a synthetic Playwright source, imported vacancies or read-only HeadHunter and Greenhouse APIs. Up to ten applications per run pass through persisted evaluation and drafting stages. Existing reviewed/terminal applications and imported historical submissions are skipped.

Unique keys protect platform/external vacancy ID, profile/vacancy application, resume/version, attempt idempotency and source feedback identity. Application revision, workflow revision and agent version prevent stale changes. AI output is schema-validated; claimed matching skills and writer facts must come from supplied evidence. Review remains mandatory.

TestSubmissionService commits Pending and Submitting before invoking the isolated provider. Confirmation produces TestConfirmed/Submitted with IsTest=true; failure produces SubmissionUnknown. The same key returns the existing attempt, never repeats the side effect. A crash can leave Pending; explicit mark-unknown records uncertainty. Real platform submission is disabled.

## Worker

TaskProcessor claims a 20-minute lease atomically. Configured timeout is 5–900 seconds, below the lease duration; no lease renewal is needed for supported bounded runs. A separate context polls cancellation every 300 ms. Completion and release commit together. Failed jobs retry with 1/2/4/8/16-minute backoff up to configured MaxRetries. Expired Running jobs become Interrupted and are reclaimed. Workflow application state permits safe resumption.

Dispatch: HealthCheck, BrowserDryRun, Workflow, Integration. Pause disables future scheduling; Stop also requests cancellation. Periodic intervals coalesce. Timezone is validated metadata; schedule arithmetic is UTC intervals, not cron. Worker process heartbeat/service packaging is not implemented.

## AI and MCP

Codex CLI uses ArgumentList and stdin, output schema and process-tree timeout. Agent/provider model dropdowns read the installed CLI's account catalog through a short-lived app-server JSON-RPC initialize/model/list connection, with pagination, a 25-second deadline and a five-minute successful-result cache. The metadata query sends no candidate data and starts no model turn. Missing saved models remain visible; a provider change does not overwrite the selected model or reasoning. Agent model overrides provider model; otherwise the catalog default is resolved, passed explicitly to CLI and recorded in AgentExecution.Model. Catalog failures are surfaced rather than guessed from a disk cache. Older executions with empty model fields cannot identify their historical model.

The host performs MCP calls before AI according to static tool bindings. Official SDK handles stdio/HTTP. Connections must be enabled; calls require explicit name allowlist and readOnlyHint. Tool output is untrusted input, capped in size. No MCP server or model-selected write tool execution is implemented.

## Imports and feedback

Browser preparation uses only vacancy IDs returned by the completed platform discovery in the current run. Cached vacancies remain stored but receive a `WorkflowVacancySkipped` event instead of being silently reprocessed. A failed search keeps checkpointed vacancies and records their IDs/URLs, without preparing them in that run. Active `FreshnessDays` is included in the evaluation input and cannot be relaxed by older profile instructions.

Publication verification first compares labelled visible publication dates with matching `JobPosting.datePosted` calendar dates, preserving explicit time-zone offsets. A conflict clears the accepted date, stores both source quotes and blocks evaluation/submission. `PublicationDateConflict` and `VacancyFreshnessChecked` retain the evidence.

Workflow audit events record discovery, skipped vacancies and reasons, evaluation decisions, letter preparation, PDF provenance and blocking stage. `AgentExecutionCompleted` records role, operation, resolved model, duration and status without retaining general output or input. Resume verification issues are stored before blocking PDF generation. The latest unread application Attention notification follows the current blocking reason. Search and Monitor use the configured agent executor, including CLI model resolution.

JournalService stages CSV rows, validates mapping and confirms them transactionally. Vacancy conflicts follow keep-local/update-vacancies. HistoricalApplication stores source status separately from locally executed attempts and blocks resubmission. Unconfirmed journal imports block approval/submission.

RemoteIntegrationService uses fixed Google API hosts, no redirect following, 90-second timeout and bounded responses. Sheets becomes a staged import. A separate export path previews a bounded snapshot and compares the local and remote values before a RAW update to a dedicated tab. Google OAuth uses a loopback callback with PKCE and stores refresh tokens in the protected secret store. Gmail reads metadata/snippet, JSON feedback uses source event IDs. Feedback is explicitly linked to an application of the same profile; this records EmployerInteraction and EmployerResponded. No outbound mail or calendar writes occur.

## Local security and storage

API defaults to 0.0.0.0:5271; ASPNETCORE_URLS can restrict the listener to loopback or a specific interface. LocalNetworkAccess accepts loopback/private peer IPs and localhost, the machine hostname or a private-IP Host. It requires X-JobFlow-Client for mutations without permissive CORS. There is no authentication within the LAN. Scope the Windows firewall rule to LocalSubnet and the LAN interface. Internet hosting requires a separate authentication/TLS design. Google OAuth initialization still runs through loopback on the API machine.

Secrets are separate encrypted files via Data Protection; Windows keys use DPAPI. Unix keys rely on filesystem permissions. Database, CVs and browser profiles rely on OS permissions; full data encryption and retention policies are not implemented. Configuration snapshots may contain user-authored prompt text, so never put tokens in prompts. Only trusted MCP executables should be configured.

Migrations apply on startup. Back up the stopped data directory before upgrading: SQLite table rebuilds may not be fully transactional. Google live credentials, Linux deployment, PostgreSQL and cross-machine restore remain unverified.
