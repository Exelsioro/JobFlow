# JobFlow

Универсальное локальное рабочее пространство поиска работы: ASP.NET Core 10, Angular 22, SQLite/EF Core, отдельный .NET Worker, Codex CLI и Playwright.

В браузерном Workflow есть три источника: «Новый поиск», «Сохранённые необработанные» и «Новый поиск + сохранённые». Сохранённая очередь работает по ссылкам из базы без повторного поиска; объединённая сначала собирает новые ссылки, затем разбирает их вместе с остатком. Готовые к проверке, отправленные и отклики с неизвестным результатом отправки не отправляются повторно. Сначала берутся вакансии без начатого отклика, затем незавершённые попытки этого Workflow; остаток после лимита сохраняется для следующего запуска. Возраст и открытый статус вакансий проверяются перед оценкой, ограничения отправки сохраняются.

Поля «Статус обработки» и «Результат последней оценки» сужают очередь по выбранному профилю. Например, «Без оценки» выбирает вакансии без его оценок; учитывается последняя оценка по времени и ID. Фильтр по оценке не является разрешением отправки: при обработке действуют проверки соответствия и актуальности. В разделе «Вакансии» такие же фильтры позволяют просматривать все статусы, включая отправленные и закрытые; там также показан статус обработки каждой вакансии.

На Windows для запуска готовой сборки используйте [scripts/start-local.cmd](scripts/start-local.cmd). Команда не меняет общую ExecutionPolicy: она разрешает выполнение только своему дочернему процессу PowerShell. Launcher читает пользовательские настройки каталога данных, .NET, браузеров и Google, пишет журналы в каталог данных и проверяет готовность API/Search/Monitor. Явный `-DataDirectory` имеет приоритет над сохранённым `JOBFLOW_DATA_DIR`.

**Приложение находится в разработке.** Браузерный workflow использует сохранённые авторизации, ищет вакансии агентом и может отправлять подходящие отклики при включённой автоотправке. Прежний режим `prepare` сохраняет подготовку с ручной проверкой. Полный статус и границы проверок — [docs/PROGRESS.md](docs/PROGRESS.md).

Поиск и мониторинг теперь запускаются отдельными процессами `JobFlow.Search` и `JobFlow.Monitor`: у них независимые очереди, расписания и агенты. Браузер принадлежит службе поиска; API передаёт команды просмотра и входа в неё. Поддержаны интервалы, ежедневное время и дни недели с часовым поясом. «Службы» показывает heartbeat, запуск, паузу и остановку; «Уведомления» — результаты запусков, письма и запросы проверки.

При поиске агент собирает потенциально подходящие вакансии по основным задачам, стеку и переносимому опыту. Неподтверждённый стаж, уровень языка, часовой пояс или пожелания работодателя сами по себе не должны скрывать такую вакансию. Отдельный оценщик различает обязательные требования и пожелания: возможное соответствие с нерешёнными обязательными вопросами получает `NeedsReview` и остаётся на ручную проверку. Подтверждённые жёсткие ограничения, актуальность, запрет повторного отклика и проверка фактов сохраняются. Новая политика передаётся при каждом вызове CLI, включая существующих агентов; ручная кнопка оценки по правилам CLI не вызывает.

В форме Workflow отдельно задаются: сбор с каждой площадки (1–200), проверки вакансий за запуск (1–500) и успешно подготовленные отклики (1–50). Поиск сначала проходит все выбранные площадки, затем проверки чередуются между ними с сохранением порядка выдачи. Ошибки и отклонения расходуют только лимит проверок. Лимиты не отменяют общий тайм-аут задания из Планировщика. В истории есть отдельные счётчики найденных и проверенных вакансий.

Workflow занимает браузерный профиль на всё время работы, включая ожидание CLI. Браузер открывается при первом обращении к площадке и закрывается после завершения, ошибки или отмены Workflow; при следующем запуске используется тот же каталог профиля. Постоянные cookies и LocalStorage сохраняются в профиле, временные cookies переносятся между запусками в памяти работающей службы. Вкладки этого профиля при завершении закрываются. Ручное открытие браузера вне Workflow остаётся доступным.

Письмо ссылается на ID фактов и дословные цитаты, которые могут быть частью исходного поля. Отдельный вызов CLI проверяет весь текст на неподтверждённые утверждения; разрешена одна попытка исправления. Если проверка снова не проходит, отклик блокируется. Ответы генерации/проверки письма и проверки актуальности сохраняются локально в AgentExecution.Output для диагностики и могут содержать сведения из досье. Для совпадающего JobPosting дата datePosted разбирается напрямую; конфликт источников и неподтверждённый открытый статус продолжают блокировать обработку. В Audit записываются модельная дата, выбранный источник и причины отказа. NeedsAttention передаётся в статус задания и уведомление.

### Внешние формы отклика

В карточке отклика есть поле «Ваше уточнение» и кнопка «Передать уточнение». Текст сохраняется для этой вакансии и профиля; прежнее одобрение снимается, а одноразовое задание заново читает вакансию, оценивает соответствие, дорабатывает письмо и резюме и проверяет факты. Для доработки письма нужен назначенный в workflow агент письма. Все переданные уточнения доступны в карточке и учитываются при последующих проверках этого отклика; общее досье профиля не меняется. Подтверждённые пользователем факты могут дополнять сведения, а просьба изменить текст сама по себе не подтверждает опыт. Статус задания обновляется в карточке. Автоотправка и автоматическая работа с внешней формой для такой доработки выключены. Старый внешний черновик теряет актуальность. После успешной обработки отклик возвращается на ручную проверку; отправленные отклики и отклики с попыткой отправки этим действием не переоткрываются.

Если кнопка отклика ведёт на внешний сайт работодателя или ATS, браузерный workflow проверяет HTTPS, публичность адреса и совпадение работодателя и вакансии по видимым цитатам. Поддерживаются ссылки, новые вкладки и редиректы. При подтверждённом совпадении агент заполняет форму и прикладывает подготовленное резюме; неизвестные ответы, регистрация и CAPTCHA передаются человеку. Внешний отклик всегда остаётся на ручную проверку и отправку, даже при включённой автоотправке. В разделе «Отклики» кнопка «Проверить внешнюю форму» показывает адрес, основания сопоставления, сохранённые поля и снимок. Заполненная вкладка сохраняется после workflow; после перезапуска браузера остаются снимок и поля. «Проверил — продолжить вручную» передаёт управление формой пользователю, после отправки нужно отметить отклик отправленным вручную.

### Запуск независимых служб

Если выбор элемента завершился ошибкой, действие не изменило страницу или агент не смог найти элемент, включается визуальный фолбэк: свежий PNG видимой области передаётся модели через CLI, затем выполняется одно действие по координатам — клик, заполнение текстового поля или прокрутка. Перед действием проверяются URL, состояние страницы, положение прокрутки и цель клика. Отправка, вход, загрузка файла и согласия через визуальный фолбэк запрещены; внешние формы остаются на ручную проверку. По умолчанию разрешено три визуальные попытки за этап в пределах общего лимита шагов. `Browser__VisualRecoveryLimit=0` отключает фолбэк, допустимый диапазон — 0–5. В Audit сохраняются операция `VisualRecovery`, координаты и результат; PNG передаётся модели, временный файл удаляется после вызова CLI.

Проверка актуальности передаёт цитаты отдельно от JSON Schema: модель выбирает ID доказательства, а код восстанавливает исходный текст. Кавычки, переносы строк и JSON-LD сайта не попадают в enum схемы ответа.

Браузер сначала обрабатывает активное модальное окно. После ошибки безопасного действия агент получает новый снимок и причину; по умолчанию разрешены три восстановления за этап. Финальная отправка и загрузка PDF автоматически не повторяются. Ожидание загрузки — 60 секунд с одним повтором GET-перехода. Параметры задаются в секции `Browser` настроек API и Worker или переменными `Browser__NavigationTimeoutSeconds` (1–180), `Browser__NavigationRetries` (0–2), `Browser__ActionTimeoutSeconds` (1–60), `Browser__ActionRecoveryLimit` (0–5). Общий тайм-аут задания в планировщике также должен покрывать весь проход.

При окончательной ошибке браузера сохраняются причина, URL, текст страницы и JPEG в `JOBFLOW_DATA_DIR/browser-diagnostics/<id>/` (по умолчанию `%LOCALAPPDATA%/JobFlow/browser-diagnostics/`). Поля пароля на снимке скрываются, значения полей ввода в текстовую диагностику не копируются. Диагностика может содержать личные данные видимой страницы; она хранится локально до удаления пользователем. В истории Workflow и журнале остаётся точная ошибка со ссылкой `/api/browser-diagnostics/<id>`; снимок доступен по этой ссылке с суффиксом `/screen`. Для старых падений снимки восстановить нельзя.

После сборки выполните `pwsh -File scripts/start-local.ps1`. Скрипт запускает API и два скрытых фоновых процесса под текущей учётной записью. Они работают после закрытия веб-страницы; автозапуск после перезагрузки требует регистрации Windows-служб.

Для Windows SCM подготовлен `scripts/install-services.ps1`: из PowerShell администратора выполните `./scripts/install-services.ps1 -Credential (Get-Credential)`. Укажите Windows-учётную запись, владеющую данными JobFlow, DPAPI-ключами и авторизацией Codex; ей нужно право «Вход в качестве службы». Скрипт публикует Worker, регистрирует две службы с автоматическим запуском и восстановлением. Пароль вводится в системном запросе PowerShell и не сохраняется в репозитории. До запуска остановите фоновые копии из раздела «Службы». Если API работает без повышения прав, его учётной записи нужно отдельно предоставить Start/Stop для этих двух служб.

Ручной запуск: `dotnet run --project src/JobFlow.Worker -- --ServiceRole search` и отдельно `dotnet run --project src/JobFlow.Worker -- --ServiceRole monitor`. Службы используют ту же `JOBFLOW_DATA_DIR`, что и API. Внутренние браузерные команды слушают только `127.0.0.1:5272`; мониторинг — `127.0.0.1:5273`. API по умолчанию передаёт управление браузером службе поиска. `Services__UseWorkerBrowser=false` оставлен для изолированных проверок старого браузерного хоста.

### Досье и адаптация резюме через CLI

Загрузите PDF с текстовым слоем, создайте CLI-агента с шаблоном «Извлечение досье», затем выберите «Извлечь досье агентом». Предложение сначала показывается в разделе «Предложения досье»; подтверждение заменяет опыт, навыки, образование, языки и досье профиля. Для сканов без текста нужен OCR вне текущей реализации.

В workflow выберите `fixed` (выбранный PDF), `select` (агент выбирает загруженный PDF) или `tailor` (агент выбирает, адаптирует и проверяет новое резюме), назначьте CLI-агента резюме и инструкции поиска. Каждый вызов получает конкретную задачу и запрет выдумывать опыт. Текст адаптации должен ссылаться на точные факты; отдельный вызов проверяет утверждения. Приложение формирует PDF из обычного текста в простом шаблоне; исполняемый код/HTML агента не запускается. Проверка моделью не заменяет человеческий просмотр при первом использовании.

Созданные файлы находятся отдельно в `resumes/generated/` и в разделе «Резюме от агентов». Сохраняются исходная версия, вакансия, вызов агента, подтверждающие факты и хеш досье. Отклик ссылается на точный созданный PDF; он и загружается на площадку. Изменение досье после подготовки блокирует отправку до повторной подготовки. Гарантии прохождения всех ATS нет.

Поиск завершает обработку одной площадки перед следующей, начиная каждый запуск со следующего источника, чтобы малый лимит не исключал остальные. По умолчанию действует ограничение свежести 7 дней: неизвестная дата или закрытая вакансия блокируют автоотправку. Поддержаны ISO, `ДД.ММ.ГГГГ`, «сегодня/вчера» и относительные дни; нераспознанная дата требует внимания. Перед отправкой выполняется повторная проверка страницы.

Gmail настраивается отдельно: выберите MailAnalysis-агента с подходящей моделью и reasoning, укажите инструкции мониторинга и создайте задание `Integration` для этой интеграции в планировщике. Новый поиск не вызывает почту. Мониторинг сам читает Gmail, классифицирует новые письма, сопоставляет их с откликами и создаёт уведомления. Неоднозначные письма остаются для ручной связи.

## Что уже работает

- Пустой запуск; создание и редактирование нескольких профилей.
- PDF до 10 МБ, версии резюме и проверка принадлежности версии профилю отклика.
- Площадки и ручной импорт вакансий; извлечение искусственной вакансии через изолированный Playwright-адаптер.
- Сохраняемый workflow поиска, структурированной/AI-оценки, генерации письма и ручного одобрения; шаблоны агентов и редактор письма.
- Создание, редактирование, копирование и отключение агентов; версии конфигурации и история выполнения.
- Реальный Codex CLI со stdin, тайм-аутом, structured output и независимой JSON Schema validation.
- Проверка тестовой браузерной формы, включая неизвестные поля, потерю авторизации и отсутствие квитанции.
- Браузерные профили для ручной авторизации, сохранение cookies, закрытие и подтверждаемое удаление.
- Состояния отклика, журнал переходов, уникальные ключи и optimistic concurrency.
- Worker: HealthCheck/BrowserDryRun/Workflow/Integration, расписание, остановка, тайм-ауты, backoff, leases и восстановление.
- CSV-экспорт вакансий с защитой от spreadsheet formula injection.
- Адаптивный Angular UI, связанный с API.
- Браузерный агент: поиск в авторизованном профиле, чтение полных страниц, заполнение формы, загрузка выбранного PDF, отправка с квитанцией и проверка Gmail в одном workflow.
- Ручной вход в браузерный профиль из веб-интерфейса по LAN: изображение вкладки, ввод текста, клавиши и прокрутка. Пароли исключаются из снимков для AI.

- MCP stdio/HTTP, discovery и разрешённые read-only инструменты агентов, отдельное защищённое хранилище секретов.
- CSV/Google Sheets import с preview/confirm, историей и запретом повторных заявок; Gmail/JSON feedback и ручная связь с откликом.
- Идемпотентная изолированная тестовая отправка, история попыток и SubmissionUnknown без повторной отправки.

HeadHunter и Greenhouse также поддерживают поиск через публичные API в режиме `prepare`. В режиме `browser` агент работает со страницами выбранных площадок в вашем браузерном профиле. Sheets поддерживает подтверждаемый импорт и отдельную вкладку экспорта. Gmail и Sheets поддерживают Google OAuth с обновлением access token. [Настройка workflow и интеграций](docs/INTEGRATIONS.md).

## Требования

- .NET 10 SDK и совместимый runtime.
- Node.js 26 (либо поддерживаемая Angular 22 версия из официальной таблицы), npm.
- PowerShell 7 для Windows-скриптов.
- Chromium Playwright; устанавливается следующей командой.
- Только для AI: отдельная установка Codex CLI в PATH и авторизация `codex login`. Для запуска остальных функций аккаунт не нужен.

## Сборка и запуск на Windows

Из корня репозитория:

```powershell
pwsh -File scripts/build.ps1
pwsh -File src/JobFlow.Api/bin/Debug/net10.0/playwright.ps1 install chromium
pwsh -File scripts/start-local.ps1
```

Для ручного запуска отдельных процессов:

```powershell
dotnet run --no-build --no-launch-profile --project src/JobFlow.Api
dotnet run --no-build --no-launch-profile --project src/JobFlow.Worker -- --ServiceRole search
dotnet run --no-build --no-launch-profile --project src/JobFlow.Worker -- --ServiceRole monitor
```

Откройте **http://127.0.0.1:5271**. API обслуживает собранный frontend. Worker нужен для заданий; закрытие вкладки не останавливает Worker. Закрытие его терминала останавливает процесс. Для регистрации двух Windows-служб используйте scripts/install-services.ps1 из PowerShell администратора.

### Доступ с другого компьютера в локальной сети

API по умолчанию слушает IPv4-интерфейсы на порту 5271 без авторизации. На другом устройстве в той же сети откройте `http://LAN_IP_КОМПЬЮТЕРА:5271`. Локальный IPv4 можно посмотреть через `Get-NetIPAddress -AddressFamily IPv4` или `ipconfig`. Разрешены localhost, имя компьютера и частные IP-адреса; запросы от публичных IP отклоняются. Доступные устройства используют одно рабочее пространство и могут изменять его данные.

Если Windows блокирует подключение, выполните PowerShell от имени администратора, заменив адрес и имя интерфейса на свои:

```powershell
New-NetFirewallRule -Name 'JobFlow-LAN-5271' -DisplayName 'JobFlow LAN' -Direction Inbound -Action Allow -Protocol TCP -LocalPort 5271 -LocalAddress '192.168.100.16' -RemoteAddress LocalSubnet -InterfaceAlias 'Ethernet' -Profile Any
```

Правило разрешает подключения из локальной подсети на выбранном интерфейсе. Чтобы снова слушать только этот компьютер, задайте `$env:ASPNETCORE_URLS = 'http://127.0.0.1:5271'` перед запуском API. Браузерные сессии и Codex выполняются на компьютере с API/Worker. При подключении Google с другого ПК страница авторизации открывается в управляемом браузерном профиле сервера: loopback callback завершается на нужном компьютере.

В локальной конфигурации общий режим браузера — видимый Chromium (`Browser:Headless=false`). В разделе «Площадки» для каждого источника можно выбрать общий режим службы, видимый Chromium, headless-shell или новый headless Chromium (`channel=chromium`). Настройка площадки применяется при поиске, чтении вакансии и отклике. При смене режима закрываются вкладки и перезапускается тот же сохранённый профиль; cookies, включая временные, переносятся в памяти, а локальное хранилище остаётся в профиле. Ручная авторизация и подготовка отклика открываются в видимом режиме. Окно появляется на компьютере с Worker, управление через веб-интерфейс также доступно. Фактический режим виден в разделе «Браузерные профили». `Browser__Headless=true` меняет общий режим автоматизации для площадок с выбором «Общий режим службы».

Для hot reload frontend:

```powershell
cd src/JobFlow.Web
npm start -- --host 127.0.0.1 --proxy-config proxy.conf.json
```

## Данные и конфигурация

По умолчанию данные находятся в каталоге `JobFlow` внутри системного LocalApplicationData. В Windows обычно это `%LOCALAPPDATA%/JobFlow`. Переопределить общий путь **одинаково для API и Worker**:

```powershell
$env:JOBFLOW_DATA_DIR = 'D:/JobFlowData'
```

Каталоги: `jobflow.db`, `resumes/`, `browser-profiles/`, `agent-work/`, `secrets/`. Секреты шифруются отдельно; Windows-ключи привязаны к пользователю через DPAPI. Временные файлы AI удаляются после выполнения. Журналы процессов выводятся в stdout в JSON. Конфигурации агентов и их снимки хранятся в БД; вход и ответ AI по умолчанию не сохраняются. Не помещайте секреты в промпты.

`JOBFLOW_CODEX_PATH` позволяет задать путь к исполняемому файлу Codex. Модель не зашита в код: укажите доступный ID в UI или оставьте пустым для выбора CLI. Reasoning должен поддерживаться выбранной моделью.

Codex запускается с игнорированием пользовательского config.toml, ephemeral-сессией, read-only sandbox и отключёнными shell/apps/browser/computer/multi-agent/hooks/image tools. Это не замена изоляции ОС. Для чувствительных данных используйте отдельную учётную запись ОС. Контроль стоимости остаётся вне JobFlow. MCP-инструменты вызываются отдельным клиентом по явному allowlist, а не самим Codex.

Браузерный агент получает снимок страницы и возвращает структурированное следующее действие. JobFlow выполняет это действие через Playwright в выбранном профиле. Для этого не требуются встроенные browser tools Codex. В снимок не включаются скрытые поля и поля паролей; значения ручного ввода не пишутся в журнал действий.

## Первая настройка

### Браузерный поиск и автоматические отклики

1. Создайте профиль кандидата, заполните подтверждённый опыт и загрузите PDF.
2. Создайте браузерный профиль. Нажмите «Управлять браузером», откройте площадки и войдите в свои аккаунты. При работе с другого ПК используйте изображение вкладки и поле ввода текста; авторизации сохраняются на сервере.
3. Добавьте площадки с адаптером `browser`: URL страницы поиска и задача поиска. В workflow можно выбрать несколько площадок; они используют один браузерный профиль.
4. Настройте включённый Codex-провайдер. Создайте агента с шаблоном «Управление браузером» (`BrowserAutomation`) и агента с шаблоном оценки (`Evaluation`). Для персонализированного письма можно назначить `CoverLetter`.
5. Для учёта ответов подключите и включите Gmail-интеграцию того же кандидата. Кнопка «Подключить Google» при доступе по LAN использует серверный браузерный профиль, показанный в веб-интерфейсе. Для мониторинга создайте отдельное задание Integration, назначьте ему Gmail-интеграцию и расписание.
6. Создайте workflow в режиме `browser`, выберите браузерный профиль, агентов, PDF, площадки и правила. Включите автоотправку, если агент должен отправлять вакансии с оценкой `Proceed`. `NeedsReview` оставляет черновик на ручную проверку.
7. Запустите API и Worker. Нажмите «Запустить workflow». Для регулярного поиска включите созданное задание в планировщике; интервал настраивается там же. Браузер работает в службе Search; API передаёт туда команды входа и управления.
8. Результаты смотрите в истории workflow, откликах и попытках отправки. `Confirmed` требует видимой квитанции; потеря подтверждения даёт `SubmissionUnknown` и запрещает автоматический повтор. Gmail проверяется службой Monitor по собственному расписанию.

Агент работает с обычными элементами страницы и доступными фреймами того же сайта. CAPTCHA, потеря авторизации, вопросы без подтверждённых ответов и неподдерживаемые виджеты требуют внимания пользователя. Переходы и отправка ограничены выбранным сайтом. Автоматическая работа на всех реальных площадках не подтверждена: сквозные проверки используют локальный HTTP-сайт и контролируемые ответы Gmail.

### Подготовка через API и импорт

1. Создайте профиль и заполните подтверждённый опыт.
2. Выберите профиль вверху и загрузите PDF.
3. Добавьте площадку. `search-only` поддерживает ручной импорт; `test-form` извлекает только встроенную искусственную вакансию и не посещает указанный URL.
4. Добавьте Codex-провайдера. Включайте его только если разрешаете передачу данных выбранному AI.
5. Создайте агента, укажите профиль/провайдера, промпт и JSON Schema. Подстановка входа: `{{input}}`.
6. Включите провайдера и агента, затем выполните проверку или ручной запуск.
7. Создайте workflow, назначьте резюме, площадку и при необходимости агентов. Включите и запустите; Worker выполнит подготовку. Проверьте оценки, письмо и одобрите отклик.
8. Настройте интеграции и расписание по [руководству](docs/INTEGRATIONS.md). Для CSV/Sheets сначала подтвердите импорт истории.
9. Ручной запуск ставит задачу в очередь; результат смотрите в «Запуски заданий» и «История workflow».

Подготовка отклика не доказывает отправку. Прямые переходы в Submitted через API переходов запрещены: используйте браузерный workflow с подтверждением или явную отметку самостоятельно отправленного отклика. Изолированный dry-run никогда не создаёт реальный отклик.

## Проверки

```powershell
dotnet test
dotnet run --project tests/JobFlow.Smoke
# Отдельная проверка реально настроенного Codex; может расходовать квоту:
dotnet run --project tests/JobFlow.Smoke -- --codex
# Проверка контракта браузерного агента реальным Codex на искусственной странице:
dotnet run --project tests/JobFlow.Smoke -- --codex-browser
# Реальный CLI: выбор, адаптация, проверка фактов и создание PDF на искусственных данных:
dotnet run --project tests/JobFlow.Smoke -- --codex-resume
```

Smoke требует предварительной сборки frontend, свободного порта 5271 и Chromium. Он запускает API/Worker с отдельной искусственной БД в игнорируемом `data/`, закрывает процессы и сохраняет снимки в игнорируемом `.impeccable/review/`. Боевые данные не используются.

## Переносимость

Скрипт `sh scripts/build.sh` предназначен для Linux. Нужны зависимости Chromium и `pwsh .../playwright.ps1 install --with-deps chromium`. Linux-запуск пока **не проверен**. Подробности: [docs/MIGRATION.md](docs/MIGRATION.md).
